## Context

项目使用 Drizzle ORM 管理数据库 schema，通过 `apps/admin/server/db/seed-sql/` 目录下的模块化脚本生成 seed 数据。当前已有 11 个 seed 模块框架，但大部分表缺少 mock 数据。项目使用 IdMapRegistry 管理表间外键关联，确保数据生成顺序正确。

**当前状态**:

- 94 个表定义在迁移文件中
- 11 个 seed 模块已存在但不完整
- 部分表有 mock-data.ts 文件，部分缺失
- `generate-seed-sql.ts` 脚本框架已就绪

**约束**:

- 不修改数据库 schema 或迁移文件
- 不修改 API 接口代码
- 必须遵循现有的 IdMapRegistry 外键关联机制
- 必须按模块依赖顺序生成数据

## Goals / Non-Goals

**Goals:**

- 为所有 94 个表创建 mock 数据生成逻辑
- 确保外键关联正确（使用 IdMapRegistry）
- 生成合理数量的测试数据（总计 1000-2000 条）
- 保持模块化结构，便于维护

**Non-Goals:**

- 不修改数据库 schema 定义
- 不创建新的 seed 模块（使用现有 11 个模块）
- 不修改 API 接口或业务逻辑
- 不处理生产环境数据迁移

## Decisions

### 决策 1: 使用现有 seed 模块结构

**选择**: 扩展现有的 11 个 seed 模块，而不是创建新模块

**理由**:

- 现有模块已按业务领域划分，结构清晰
- 模块间依赖关系已定义（00-dev → 01-community → ... → 10-report）
- 避免破坏现有的 IdMapRegistry 机制

**替代方案**:

- 创建单一的大型 seed 文件 → 难以维护，违反模块化原则
- 按表创建独立 seed 文件 → 外键关联复杂，难以管理依赖

### 决策 2: Mock 数据存储位置

**选择**: 在 `apps/admin/server/api/{path}/mock-data.ts` 创建 mock 数据文件

**理由**:

- 与现有项目约定一致
- Mock 数据与 API 路由在同一目录，便于查找
- 支持按业务路径组织数据

**替代方案**:

- 集中存储在 `seed-sql/` 目录 → 与 API 代码分离，不符合项目约定
- 使用 faker 动态生成 → 数据不稳定，难以复现问题

### 决策 3: 数据量设计

**选择**: 每个模块生成 20-500 条数据，总计约 1000-2000 条

**理由**:

- 足够支持前端页面展示和分页测试
- 不会导致数据库过大影响性能
- 能够覆盖各种业务场景（正常、异常、边界）

**数据量分配**:
| 模块 | 表数量 | 数据量 | 理由 |
|------|--------|--------|------|
| dev | 9 | 20-50 | 配置数据，数量较少 |
| community | 6 | 50-100 | 社区基础数据 |
| setting | 13 | 100-200 | 组织架构和权限数据 |
| house-property | 11 | 200-500 | 核心业务数据，需要较多 |
| operation | 9 | 50-100 | 运营管理数据 |
| contract | 11 | 50-100 | 合同数据 |
| parking | 5 | 50-100 | 停车数据 |
| expense | 16 | 200-500 | 费用数据，业务复杂 |
| patrol | 6 | 50-100 | 巡检数据 |
| repairs | 7 | 100-200 | 报修数据 |
| report | 12 | 100-200 | 报表数据 |

### 决策 4: 外键关联处理

**选择**: 使用 IdMapRegistry 管理所有外键关联

**理由**:

- 项目已有成熟的 IdMapRegistry 机制
- 自动处理 ID 映射，避免硬编码
- 支持跨模块的外键引用

**实现方式**:

```typescript
// 主表数据生成
const communityId = idMap.register("cm_communities", mockCommunity.id);

// 从表引用
const house = {
	...mockHouse,
	communityId: idMap.get("cm_communities", mockHouse.communityId),
};
```

## Risks / Trade-offs

### 风险 1: Mock 数据与实际业务逻辑不符

**风险**: 手动创建的 mock 数据可能不符合业务规则（如状态流转、金额计算）

**缓解措施**:

- 参考现有 API 的 mock-data.ts 文件
- 与前端页面对照，确保数据能正常展示
- 在 tasks.md 中添加验证步骤

### 风险 2: 外键关联错误

**风险**: 跨模块的外键引用可能出错，导致数据孤岛

**缓解措施**:

- 严格按照模块依赖顺序生成数据
- 使用 IdMapRegistry 统一管理 ID 映射
- 在生成 SQL 后执行验证查询

### 风险 3: 数据量过大影响性能

**风险**: 如果数据量过大，可能导致 SQL 执行缓慢或数据库性能下降

**缓解措施**:

- 控制每个模块的数据量（见决策 3）
- 分模块生成和执行 SQL
- 提供清理脚本，便于重置数据

### Trade-off: 手动创建 vs 自动生成

**选择**: 手动创建 mock 数据文件

**优点**:

- 数据稳定，便于复现问题
- 可以精确控制数据内容
- 符合项目现有约定

**缺点**:

- 工作量较大（需要创建多个 mock-data.ts 文件）
- 数据更新需要手动维护

**理由**: 项目已有手动创建 mock 数据的约定，保持一致性更重要

## Migration Plan

### 部署步骤

1. **准备阶段**
   - 确认数据库迁移已运行（`pnpm db:migrate`）
   - 备份现有数据（如果有）

2. **数据生成阶段**
   - 按模块顺序创建 mock-data.ts 文件
   - 扩展对应的 seed-sql 模块
   - 运行 `pnpm run generate-seed-sql --module <name>` 验证单个模块

3. **执行阶段**
   - 生成完整 SQL：`pnpm run generate-seed-sql`
   - 执行 SQL 到数据库
   - 验证数据完整性

4. **验证阶段**
   - 检查每个表的数据量
   - 验证外键关联正确
   - 在前端页面测试数据展示

### 回滚策略

如果数据填充出现问题：

1. **清空数据库**

   ```sql
   TRUNCATE TABLE <table_name> CASCADE;
   ```

2. **重新运行迁移**

   ```bash
   pnpm db:drop && pnpm db:migrate
   ```

3. **重新生成和执行 SQL**

### 验证检查点

- [ ] 所有 94 个表都有数据
- [ ] 外键关联无错误（无孤立记录）
- [ ] 数据量符合预期（1000-2000 条）
- [ ] 前端页面能正常展示数据
- [ ] 分页、筛选、排序功能正常

## Open Questions

1. **是否需要为每个表生成边界数据？**
   - 例如：空字符串、null 值、极大/极小数值
   - 建议：先生成正常数据，后续根据测试需求补充

2. **是否需要生成历史数据？**
   - 例如：不同时间段的费用记录、报修记录
   - 建议：生成近 3 个月的数据，覆盖常见时间查询场景

3. **是否需要生成多社区数据？**
   - 当前设计假设单社区场景
   - 建议：先生成 2-3 个社区的数据，测试多社区切换功能
