# 将 form.ts 文件业务类型迁移到类型包

## 概述

本变更旨在将后台项目所有 `form.ts` 文件中的业务类型定义迁移到 `@01s-11comm/type` 类型包中，实现业务类型的集中管理，避免重复定义，提升类型复用性和维护性。

## 问题背景

当前后台项目中，`form.ts` 文件包含了大量的业务类型定义（如 `xxxFormVO`），这些类型分散在各个页面组件中，存在以下问题：

1. **类型重复定义**：相同的业务类型可能在多个 form.ts 文件中重复定义
2. **维护困难**：当业务类型发生变化时，需要同步修改多个文件
3. **类型复用性差**：其他模块难以复用这些类型定义
4. **命名不规范**：部分类型和字段使用中文命名，不符合编码规范

## 解决方案

将 `form.ts` 文件中的业务类型按照模块化原则迁移到类型包的对应目录中，同时保留必要的本地定义（如 `defaultForm` 和表单 props 类型）。

### 迁移范围

基于 `apps/admin/src/router/rank/rank-route-keys.ts` 提供的路由结构，确定以下迁移范围：

- **一级模块**：settingManage、devTeam、operationTeam、propertyManage
- **二级模块**：各一级模块下的子模块
- **三级模块**：具体的业务功能页面

### 迁移内容

1. **业务类型迁移**：将 `xxxFormVO` 等业务类型迁移到类型包
2. **下拉选项迁移**：将公共下拉选项迁移到 `business-options.ts`
3. **命名规范化**：将中文命名的类型和字段统一改为英文
4. **Props 类型增强**：为所有表单 props 类型添加可选的 `mode` 字段

### 保留内容

以下内容保留在 `form.ts` 文件中，不进行迁移：

1. `defaultForm` 常量定义
2. 表单 props 类型定义（`xxxFormProps`）
3. 组件特定的本地类型

## 预期收益

1. **类型集中管理**：所有业务类型集中在类型包中，便于维护
2. **提升复用性**：其他模块可以方便地复用业务类型
3. **减少重复**：避免相同类型的重复定义
4. **规范命名**：统一使用英文命名，提升代码质量
5. **增强扩展性**：为表单模式切换提供类型支持

## 实施计划

本变更将按照以下步骤逐步实施：

1. 分析现有 form.ts 文件结构，识别需要迁移的业务类型
2. 创建或更新类型包中的对应业务类型文件
3. 将业务类型迁移到类型包，并保留 jsdoc 注释
4. 更新 form.ts 文件，导入迁移后的类型
5. 为表单 props 类型添加 mode 字段
6. 验证类型检查，确保迁移后功能正常

## 风险评估

- **低风险**：迁移过程中可能出现的类型引用错误
- **缓解措施**：严格按照步骤实施，及时运行类型检查验证
