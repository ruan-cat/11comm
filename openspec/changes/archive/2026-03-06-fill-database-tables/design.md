## Context

项目使用 Drizzle ORM 管理数据库 schema，通过 `apps/admin/server/db/seed-sql/` 目录下的模块化脚本生成 seed 数据。当前已有 11 个 seed 模块框架，但大部分表缺少 mock 数据。项目使用 IdMapRegistry 管理表间外键关联，确保数据生成顺序正确。

**当前状态**:

- 94 个表定义在迁移文件中
- 11 个 seed 模块已存在但不完整
- 部分表有 mock-data.ts 文件，部分缺失
- `generate-seed-sql.ts` 脚本框架已就绪

**约束**:

- 不修改数据库 schema 或迁移文件
- 不修改 API 接口代码
- 必须遵循现有的 IdMapRegistry 外键关联机制
- 必须按模块依赖顺序生成数据

## Goals / Non-Goals

**Goals:**

- 为所有 94 个表创建 mock 数据生成逻辑
- 确保外键关联正确（使用 IdMapRegistry）
- 生成合理数量的测试数据（总计 1000-2000 条）
- 保持模块化结构，便于维护

**Non-Goals:**

- 不修改数据库 schema 定义
- 不创建新的 seed 模块（使用现有 11 个模块）
- 不修改 API 接口或业务逻辑
- 不处理生产环境数据迁移

## Decisions

### 决策 1: 使用现有 seed 模块结构

**选择**: 扩展现有的 11 个 seed 模块，而不是创建新模块

**理由**:

- 现有模块已按业务领域划分，结构清晰
- 模块间依赖关系已定义（00-dev → 01-community → ... → 10-report）
- 避免破坏现有的 IdMapRegistry 机制

**替代方案**:

- 创建单一的大型 seed 文件 → 难以维护，违反模块化原则
- 按表创建独立 seed 文件 → 外键关联复杂，难以管理依赖

### 决策 2: Mock 数据存储位置

**选择**: 在 `apps/admin/server/api/{path}/mock-data.ts` 创建 mock 数据文件

**理由**:

- 与现有项目约定一致
- Mock 数据与 API 路由在同一目录，便于查找
- 支持按业务路径组织数据

**替代方案**:

- 集中存储在 `seed-sql/` 目录 → 与 API 代码分离，不符合项目约定
- 使用 faker 动态生成 → 数据不稳定，难以复现问题

### 决策 3: 数据量设计

**选择**: 每个模块生成 20-500 条数据，总计约 1000-2000 条

**理由**:

- 足够支持前端页面展示和分页测试
- 不会导致数据库过大影响性能
- 能够覆盖各种业务场景（正常、异常、边界）

**数据量分配**:
| 模块 | 表数量 | 数据量 | 理由 |
|------|--------|--------|------|
| dev | 9 | 20-50 | 配置数据，数量较少 |
| community | 6 | 50-100 | 社区基础数据 |
| setting | 13 | 100-200 | 组织架构和权限数据 |
| house-property | 11 | 200-500 | 核心业务数据，需要较多 |
| operation | 9 | 50-100 | 运营管理数据 |
| contract | 11 | 50-100 | 合同数据 |
| parking | 5 | 50-100 | 停车数据 |
| expense | 16 | 200-500 | 费用数据，业务复杂 |
| patrol | 6 | 50-100 | 巡检数据 |
| repairs | 7 | 100-200 | 报修数据 |
| report | 12 | 100-200 | 报表数据 |

### 决策 4: 外键关联处理

**选择**: 使用 IdMapRegistry 管理所有外键关联

**理由**:

- 项目已有成熟的 IdMapRegistry 机制
- 自动处理 ID 映射，避免硬编码
- 支持跨模块的外键引用

**实现方式**:

```typescript
// 主表数据生成
const communityId = idMap.register("cm_communities", mockCommunity.id);

// 从表引用
const house = {
	...mockHouse,
	communityId: idMap.get("cm_communities", mockHouse.communityId),
};
```

## Risks / Trade-offs

### 风险 1: Mock 数据与实际业务逻辑不符

**风险**: 手动创建的 mock 数据可能不符合业务规则（如状态流转、金额计算）

**缓解措施**:

- 参考现有 API 的 mock-data.ts 文件
- 与前端页面对照，确保数据能正常展示
- 在 tasks.md 中添加验证步骤

### 风险 2: 外键关联错误

**风险**: 跨模块的外键引用可能出错，导致数据孤岛

**缓解措施**:

- 严格按照模块依赖顺序生成数据
- 使用 IdMapRegistry 统一管理 ID 映射
- 在生成 SQL 后执行验证查询

### 风险 3: 数据量过大影响性能

**风险**: 如果数据量过大，可能导致 SQL 执行缓慢或数据库性能下降

**缓解措施**:

- 控制每个模块的数据量（见决策 3）
- 分模块生成和执行 SQL
- 提供清理脚本，便于重置数据

### Trade-off: 手动创建 vs 自动生成

**选择**: 手动创建 mock 数据文件

**优点**:

- 数据稳定，便于复现问题
- 可以精确控制数据内容
- 符合项目现有约定

**缺点**:

- 工作量较大（需要创建多个 mock-data.ts 文件）
- 数据更新需要手动维护

**理由**: 项目已有手动创建 mock 数据的约定，保持一致性更重要

## Migration Plan

### 部署步骤

1. **准备阶段**
   - 确认数据库迁移已运行（`pnpm db:migrate`）
   - 备份现有数据（如果有）

2. **数据生成阶段**
   - 按模块顺序创建 mock-data.ts 文件
   - 扩展对应的 seed-sql 模块
   - 运行 `pnpm run generate-seed-sql --module <name>` 验证单个模块

3. **执行阶段**
   - 生成完整 SQL：`pnpm run generate-seed-sql`
   - 执行 SQL 到数据库
   - 验证数据完整性

4. **验证阶段**
   - 检查每个表的数据量
   - 验证外键关联正确
   - 在前端页面测试数据展示

### 回滚策略

如果数据填充出现问题：

1. **清空数据库**

   ```sql
   TRUNCATE TABLE <table_name> CASCADE;
   ```

2. **重新运行迁移**

   ```bash
   pnpm db:drop && pnpm db:migrate
   ```

3. **重新生成和执行 SQL**

## Open Questions

   - 例如：不同时间段的费用记录、报修记录

3. **是否需要生成多社区数据？**
   - 当前设计假设单社区场景
   - 建议：先生成 2-3 个社区的数据，测试多社区切换功能

## Agent Team Execution Model

### 团队架构

本任务采用 **Agent Team 并行协作模式** 以提高执行效率和代码质量：

```plain
主代理 (Team Lead)
├── 技能指导子代理 (Skill Guide) - 常驻
├── 审核子代理 (Code Reviewer) - 常驻
└── 代码编写子代理 (Code Writer) - 动态创建/删除
    ├── Writer-1: 处理 dev 模块
    ├── Writer-2: 处理 community 模块
    └── Writer-N: 处理其他模块
```

### 子代理职责

#### 1. 技能指导子代理 (Skill Guide)

**职责**:

- 全面学习 `.claude/skills/` 目录下的所有技能文档
- 掌握项目代码规范、类型定义规范、Schema 编写标准
- 为代码编写子代理提供实时指导和规范咨询

**关键技能**:

- `code-style` - 代码风格规范
- `type-project-organization` - 类型项目组织规范
- `project-schema-registry` - Schema 定义标准
- `schema-and-seed-guardian` - Seed 数据生成规范
- `nitro-api-development` - Nitro API 开发规范

**工作模式**:

- 任务开始时创建，全程保持活跃
- 不直接编写代码，只提供咨询和指导
- 维护一份"常见问题和最佳实践"文档

#### 2. 审核子代理 (Code Reviewer)

**职责**:

- 审查代码编写子代理的输出
- 验证代码符合项目规范和技能要求
- 检查外键关联、数据一致性、命名规范
- 提供改进建议或批准代码

**审核清单**:

- [ ] Mock 数据格式符合 `mock-data.ts` 规范
- [ ] Seed 脚本正确使用 IdMapRegistry
- [ ] 外键引用正确，无孤立记录
- [ ] 数据量符合设计要求
- [ ] 代码风格符合 `code-style` 技能
- [ ] TypeScript 类型定义正确

**工作模式**:

- 任务开始时创建，全程保持活跃
- 每个代码编写子代理完成任务后，进行审核
- 审核不通过时，要求代码编写子代理修改

#### 3. 代码编写子代理 (Code Writer)

**职责**:

- 根据 tasks.md 中的具体任务，创建或修改文件
- 咨询技能指导子代理，确保符合规范
- 提交代码给审核子代理审查
- 根据审核反馈进行修改

**工作流程**:

1. 接收主代理分配的任务（例如："处理 dev 模块的 9 个表"）
2. 咨询技能指导子代理，了解相关规范
3. 逐个创建 mock-data.ts 文件
4. 扩展对应的 seed-sql 模块
5. 提交给审核子代理审查
6. 根据反馈修改（如需要）
7. 标记任务完成，等待删除

**工作模式**:

- 动态创建，一次只处理一个模块
- 完成任务后立即删除，释放资源
- 一次只处理一个文件，避免冲突

### 并行策略

#### 模块间串行

由于模块间存在依赖关系（外键引用），必须严格按顺序执行：

```plain
dev (00) → community (01) → setting (02) → house-property (03) → ...
```

**原因**:

- `community` 模块的表可能引用 `dev` 模块的字典数据
- `house-property` 模块的表引用 `community` 模块的社区数据
- IdMapRegistry 需要按顺序注册 ID

#### 模块内并行

同一模块内的表可以并行处理（如果资源允许）：

```plain
dev 模块 (9 个表):
  Writer-1: dt_dictionaries, dt_dictionary_items, dt_cache_configs
  Writer-2: dt_config_types, dt_configs, dt_config_items
  Writer-3: dt_menu_groups, dt_menu_catalogs, dt_menu_items
```

**条件**:

- 表之间无直接外键依赖
- 主代理资源充足（可创建多个子代理）
- 审核子代理能够处理并发审查

**限制**:

- 每个子代理一次只处理一个文件
- 避免同时修改同一个 seed-sql 模块文件

### 性能优化

#### Token 节省

- 技能学习只进行一次（技能指导子代理）
- 代码审核由专职子代理完成，主代理无需重复审查
- 代码编写子代理完成后立即删除，释放资源

#### 执行效率

- 模块内并行处理（如果资源允许）
- 避免重复的文件读取（技能指导子代理缓存规范）
- 批量提交审核（审核子代理可以批量处理）

#### 质量保证

- 专职技能指导子代理，确保规范一致性
- 专职审核子代理，全程监督代码质量
- 主代理只负责任务调度，不参与具体实现

### 最佳实践

1. **一次一个模块**: 不要同时处理多个模块，避免依赖混乱
2. **一次一个文件**: 代码编写子代理一次只处理一个文件
3. **及时删除**: 代码编写子代理完成任务后立即删除
4. **保持沟通**: 子代理之间通过主代理协调，避免直接通信
5. **记录进度**: 主代理及时更新 tasks.md 和 progress.md
6. **审核优先**: 代码必须通过审核才能标记完成
7. **错误重试**: 失败的任务最多重试 2 次，超过则人工介入
